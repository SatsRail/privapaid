# Backups and Restore

What to back up, how often, and how to restore. A PrivaPaid backup has three components and missing any one of them means data loss.

## What you need to back up

| Item | Where it lives | If lost |
|---|---|---|
| Postgres database | Your DB | Every channel, media, product, encrypted blob gone |
| `SK_ENCRYPTION_KEY` | Env var or `/app/data/.generated-env` | Can't decrypt stored merchant API key. Re-run setup wizard with a fresh SatsRail key. |
| `CONTENT_KEK` | Env var or `/app/data/.generated-env` | Lose operator-side rotation + admin preview for all envelope-encrypted content. See [[Missing CONTENT_KEK]]. |
| `NEXTAUTH_SECRET` | Same | All admin sessions invalidated. Annoying but not catastrophic. |

The DB backup is useless without the two keys. The keys are useless without the DB. Back up all three to independent locations.

## Postgres backups

### Managed Postgres (RDS / Supabase / Neon / Railway)

Use the provider's built-in automated backups. They're cheap and well-tested:

- **RDS:** Enable automated backups with 7+ day retention. Snapshots before major operations.
- **Supabase:** Daily backups on free tier; PITR on Pro.
- **Neon:** Branching gives you free point-in-time recovery.
- **Railway:** Snapshot feature on paid plans.

For all of these, the backup runs at the provider's infrastructure level and includes everything in the cluster.

### Self-hosted Postgres (Docker Compose)

Daily backup cron job:

```bash
# /etc/cron.daily/privapaid-backup
#!/bin/bash
set -e
BACKUP_DIR=/var/backups/privapaid/$(date +%Y%m%d)
mkdir -p "$BACKUP_DIR"
docker compose -f /home/ec2-user/privapaid/docker-compose.yml exec -T postgres \
  pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom \
  > "$BACKUP_DIR/privapaid.dump"

# Keep last 30 days
find /var/backups/privapaid -maxdepth 1 -mtime +30 -exec rm -rf {} +
```

```bash
sudo chmod +x /etc/cron.daily/privapaid-backup
```

Ship the dump off-server to S3 / Backblaze / Wasabi nightly:

```bash
aws s3 sync /var/backups/privapaid s3://your-backup-bucket/privapaid/ \
  --storage-class STANDARD_IA \
  --exclude "*" --include "*.dump"
```

S3 + a lifecycle policy that transitions to Glacier after 30 days is a $1/month backup strategy for typical PrivaPaid data sizes.

## Key backups

The keys aren't in Postgres. They live in `.env` (production) or `/app/data/.generated-env` (auto-generated by entrypoint). **Both files must be backed up off-server** — same logic as a Bitcoin seed phrase.

### Required backup destinations

Pick **three** independent locations. Industry-standard "3-2-1" rule for irreplaceable data:

1. Password manager entry (1Password, Bitwarden) — for daily access
2. Encrypted cloud storage (AWS Secrets Manager, GCP Secret Manager) — for ops automation
3. Printed paper backup in a physical safe — last-resort recovery

Each entry should contain all three keys with timestamps:

```
PrivaPaid production — created 2026-05-26
SK_ENCRYPTION_KEY=<value>
CONTENT_KEK=<value>
NEXTAUTH_SECRET=<value>
```

### On platforms that auto-generate

EC2 + Docker Compose entrypoint auto-generates missing keys and persists to `/app/data/.generated-env`. Copy this file off the server immediately:

```bash
ssh ec2-user@yourdomain.com 'sudo cat /home/ec2-user/privapaid/.docker-data/.generated-env' \
  | gpg --encrypt -r your@email.com > generated-env.gpg
```

Store `generated-env.gpg` in your password manager as an attachment.

## Restore procedure

### Restore Postgres

```bash
# 1. Stop the app to prevent writes mid-restore
docker compose stop app

# 2. Restore the dump
docker compose exec -T postgres pg_restore \
  --clean --if-exists \
  -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  < /var/backups/privapaid/20260526/privapaid.dump

# 3. Restart
docker compose start app
```

### Restore keys

Set the three keys back in `.env` (or via your platform's env-var UI) from your password manager. Restart the container. The entrypoint reads them and the app boots.

### Verify after restore

1. `curl https://yourdomain.com/api/health` → expect 200 with `db: connected`
2. Log in as admin → existing channels and media visible
3. Open an admin preview of an article → should decrypt successfully (proves `CONTENT_KEK` matches)
4. Log in as a buyer who previously paid → existing macaroon should still grant access (proves Postgres restored cleanly + SatsRail key matches via `SK_ENCRYPTION_KEY`)

## Disaster recovery test

Run a full restore against a staging environment quarterly:

```bash
# 1. Spin up a fresh Postgres + app container with the SAME keys
# 2. Restore the latest backup
# 3. Verify all four checks above
```

This is the only way to know your backups actually work. Most operators learn theirs don't *during the actual disaster*.
